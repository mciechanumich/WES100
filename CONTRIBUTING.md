## Who can contrubte

We expect 100th Anniversary committee members will be the people contributing to this site.
We also welcome other alumni from the Wayne Engineering Society (WES) as well as WES student members to contribute. Just submit a PR. 

## Team members

Mark C. is the github project owner.

## 🐛 How to Report a Bug

Before submitting a new bug report, please **search existing issues** to make sure it hasn't already been reported.

If it is a new bug, please open an issue and include:
*   **Clear Title**: A concise summary of the issue.
*   **Description**: What happens, what you expected to happen, and steps to reproduce.
*   **Environment**: OS, browser version, runtime/language version, and package version.
*   **Screenshots/Logs**: Any visual aids or stack traces that help diagnose the problem.

## 💡 How to Suggest a Feature

We love new ideas! To suggest a feature, open an issue and provide:
*   **Problem Statement**: Explain what problem this feature solves.
*   **Proposed Solution**: Describe how you envision the feature working.
*   **Alternatives**: Any alternative solutions or workarounds you have considered.

## 🛠️ How to Contribute Code

### 1. Environment Setup
To set up the project locally on your machine:
1. Fork the repository on GitHub.
2. Clone your fork: `git clone https://github.com`

### 2. Branching Strategy
*   Always create a new branch from `main` for your changes.
*   Name your branch descriptively: `fix/bug-name` or `feature/feature-name`.

### 3. Coding Standards
*   Follow the project's existing code style and formatting rules.
*   Ensure your code passes all linting tests: `[insert lint command]`
*   Write or update tests for any new logic or bug fixes.

### 4. Submitting a Pull Request (PR)
When your changes are ready, submit a PR against the `main` branch:
*   **Link to Issues**: Reference any related issues in the PR description (e.g., `Closes #123`).
*   **Keep it Focused**: Submit one PR per feature or bug fix. Avoid mixing unrelated changes.
*   **Update Documentation**: If your change modifies how something works, update the `README.md` or relevant docs.
*   **CI/CD**: Ensure that all automated GitHub Actions tests and checks pass.

## 👥 Code Review Process

All pull requests require review and approval from a project maintainer before merging. 
*   **Response Time**: Maintainers usually review submissions within [e.g., 2-3 business days].
*   **Feedback**: Be prepared to answer questions or make revisions based on review feedback.
